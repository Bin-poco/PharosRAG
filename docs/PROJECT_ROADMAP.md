# 技术文档 Agentic RAG 学习与改造路线

目标不是“把别人的仓库跑起来”，而是把 Pharos 改造成你能独立解释、演示、评估和部署的技术文档知识库。按里程碑推进，每一阶段都要有可运行结果和可量化证据。

## 最终技术栈

- 后端：FastAPI、Pydantic、OpenAI-compatible LLM API
- RAG：MinerU、结构化 chunk、Dense + Sparse 混合检索、Rerank、引用溯源
- Agentic：MCP 工具、查询改写、多跳检索、工具选择、失败降级
- 数据：Qdrant；Redis 只在加入异步任务后引入；PostgreSQL 留给用户、文档任务和审计元数据
- 工程：Docker Compose、pytest、离线评估集、结构化日志、健康检查
- 部署：本地 Mac 开发，后续迁移到云服务器

## 阶段 1：跑通并读懂主链路（第 1 周）

交付标准：

- Qdrant、在线推理适配器、Pharos 三个容器可启动；
- 导入 5–10 篇同一主题的公开技术文档；
- 能演示 `/v1/retrieve` 与 `/v1/ask`，答案带来源；
- 能画出“一次问题从 API 到答案”的调用链，并定位对应代码。

重点阅读顺序：`service.py` → `engine.py` → `retrieve.py` → `store.py` → `chunker/` → `generator/`。不要从第一行顺序读完整仓库。

## 阶段 2：做出自己的数据与评估（第 2 周）

选择一个清晰领域，例如 Kubernetes + FastAPI + Docker 官方文档。建立至少 30 篇文档、50 个问题的评估集，问题覆盖事实问答、跨章节问答、表格问答、无答案问题和权限问题。

至少对比：

- Dense 与 Hybrid；
- 是否 Rerank；
- 两种 chunk 大小；
- 不同 `top_k`。

记录 Recall@K、MRR、答案正确率、引用正确率、P95 延迟和单次成本。简历价值主要来自这些实验，而不是代码行数。

## 阶段 3：补齐真正的 Agentic RAG（第 3 周）

保留现有 MCP 工具面，新增一个可观察的 Agent 工作流：

1. 判断问题是否需要检索；
2. 生成或改写检索词；
3. 首次检索；
4. 证据不足时按文档、章节或表格继续检索；
5. 合并证据、去重并生成带引用答案；
6. 达到最大轮数仍证据不足时明确拒答。

每一步输出 trace，限制最大工具调用次数，并用评估集证明多跳策略在哪些问题上优于一次性 RAG。仅仅“接了 MCP”不算完成 Agentic RAG。

## 阶段 4：从命令行项目变成产品（已完成后端文档管理，前端待做）

已完成 FastAPI 文档管理 API：Markdown/PDF 上传、任务状态、数据库管理列表、失败重试、重建索引、ACL 更新和软删除。耗时解析采用 PostgreSQL + Outbox 保存事实状态，Redis + Celery 负责投递与执行；Redis 不承担文档、任务或向量的永久存储。实现和故障恢复细节见 `docs/RELIABLE_UPLOAD_JOBS.md` 与 `docs/DOCUMENT_LIFECYCLE.md`。

同时补一个轻量前端，至少包含：

- 文档上传和处理进度；
- 带来源卡片的对话页；
- 检索过程/Agent trace 展示；
- 管理员文档列表。

## 阶段 5：工程化与部署（第 5 周）

补齐 CI、日志、指标、限流、异常重试、数据备份和云服务器部署。将开发 Compose 与部署 Compose 分离，生产环境关闭热更新、使用随机密钥、HTTPS 和持久卷。

最终演示必须包含：正常问答、跨文档多跳、无依据拒答、文档新增后可检索、服务重启数据仍存在，以及一张评估结果表。

## 每周学习方法

每个功能都按“先画链路 → 打断点或加日志 → 改一个变量 → 写测试 → 做对比实验 → 用自己的话记录设计取舍”完成。每周至少提交一个独立、可解释的功能分支，不要把上游历史直接当成自己的工作成果。

简历描述应只写你亲自改造和测量的部分，例如：“将 CUDA-only 推理层改造成 DashScope 在线适配层，支持 Apple Silicon 开发；构建 50 问评估集，将 Recall@5 从 X 提升到 Y；设计带最大轮数和证据阈值的多跳 Agent 工作流。”其中 X/Y 必须来自真实实验。
